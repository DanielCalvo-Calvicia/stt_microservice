## Goal

Build `oblivion/stt:local` with the deployment tool on amd64 with Python 3.12 (the Dockerfile default, F8) and see that it builds from the requirements as the tool filters them, without compiling anything, without the dev tools and without trying to fetch models at build time.

## Read first

The preconditions of [T-03](T-03_docker-and-arm64-acceptance.md), `deployment/docker/service.Dockerfile`, `deployment/infrastructure/outbound/runtime/docker_runtime.py`, `deployment/docs/DEPLOYMENT.md` (Docker).

## Files

None changed. The tool builds in its own work directory (`<workdir>/build/stt`).

## Steps

1. With the maintainer's yes (network, disk), the maintainer sets stt to `runtime = "docker"` in their own `deployment/config/local/stt.toml` (restore it at the end) and, for a local engine, `STT_ENGINE = "local"`; say which `git` source the run uses (pushed branch or a local checkout, see the preconditions).
2. `oblivion.py deploy --host <machine> -s stt --dry-run` first and read the `docker build` line: it must not carry a `PREPARE` build argument for stt (T-02.3) and must carry no `APT_PACKAGES` (stt has none).
3. Then the real build through the tool (`deploy`, or only the build if the tool offers it; otherwise by hand from `<workdir>/build/stt`: `docker --context desktop-linux build -f <repo>\deployment\docker\service.Dockerfile -t oblivion/stt:local .`).
4. Read the output: every `pip install` step ends without compiling a wheel from source (look for `Building wheel`); note the versions of fastapi, numpy, faster-whisper, ctranslate2 and onnxruntime; note that `shared-logging` is installed from `libs/`.
5. `docker --context desktop-linux image ls oblivion/stt:local` for the size; note the build time.

## Acceptance criteria

- The build succeeds on Python 3.12 and compiles nothing.
- The build output has no `warning: prepare step failed` line for stt (it does not run `prepare`).
- The size and the time are in *Notes*.

## Verification

The relevant lines of the build output, the size and the time, in *Notes*.

## Notes

Python 3.12 has not been exercised for stt before in a container; the audit's dry-run (F16) resolved the wheels but nothing was installed. If a package fails, record its name and message and decide with the maintainer whether to change `PYTHON_VERSION` for this service (a catalogue setting) rather than patch the Dockerfile.

## Result (2026-11-09)

**Setup.** Docker Desktop 29.5.2, linux/amd64, active context `desktop-linux` (every command named it). Source: a throw-away git repo made from a copy of the stt **working tree** (without `windows/`, `.git`, `.env*`, caches; commit `1a34b4f` in the session scratchpad), pointed at by `git = "<path>"` in a scratch config folder (`oblivion.py --config`, one machine with stt only, `runtime = "docker"`, `STT_ENGINE = "local"`, `STT_GATE_ENABLED = 1`); the maintainer's `config/local/` was not touched. The tool cloned it and built from its own build folder. So the image holds the unpushed T-01 work and the contracts 0.16.0 wheel.

**Build** (inside `oblivion.py deploy`): succeeded; `RUN pip install` 29.7 s, export 22.7 s; the whole deploy (build, prepare, start, health) took 1 min 56 s. The `docker build` line carries no `PREPARE` and no `APT_PACKAGES` argument, and the last Dockerfile step ran as `RUN if [ -n "" ]; ...` for 0.3 s: no `warning: prepare step failed` anywhere (0 matches). Compiled nothing: 0 matches for `Building wheel`, `setup.py`, `.tar.gz`, `gcc`; every package is a binary wheel (`manylinux` for ctranslate2 4.8.5, onnxruntime 1.31.1, av 19.0.2, numpy 2.5.4, pydantic-core 2.50.4) and `shared-logging 0.1.0` came from `libs/`. Installed: fastapi 0.162.0, uvicorn 0.54.0, faster-whisper 1.2.1, openai 3.46.0, contracts-microservice 0.16.0. Python in the image: 3.12.16. Image `oblivion/stt:local`: **865 MB on disk**, amd64/linux, `Cmd` `python main.py`. No dev tools (T-03.4). No package failed on 3.12, so `PYTHON_VERSION` stays.
