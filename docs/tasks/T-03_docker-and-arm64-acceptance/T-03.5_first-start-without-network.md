## Goal

Observe, in a container, what the audit and F11 only read: with an empty model cache and no network the local engine cannot start, the process exits, and the container's restart policy loops it; with a filled volume it starts offline.

## Read first

[T-01.1.5](../T-01_deployment-readiness/T-01.1_baseline-checks/T-01.1.5_failure-drills.md) (the same drill natively), F11, `deployment/infrastructure/outbound/runtime/docker_runtime.py` (`--restart unless-stopped`).

## Files

None changed. Use **throw-away** names so the real volume and container stay untouched: a volume `stt-drill-empty` and a container `stt-drill`, both removed at the end.

## Steps

1. Empty volume, no network, by hand (the tool cannot disable the network): 
   ```powershell
   docker --context desktop-linux volume create stt-drill-empty
   docker --context desktop-linux run -d --name stt-drill --restart unless-stopped --network none --mount type=volume,source=stt-drill-empty,target=/models -e HF_HOME=/models/huggingface -e STT_ENGINE=local -e SERVICE_HOST=0.0.0.0 oblivion/stt:local
   ```
   (the engine and the host are given as variables of this throw-away container only; no key is involved). After a minute, `docker --context desktop-linux ps -a`, `docker --context desktop-linux inspect -f "{{.RestartCount}} {{.State.Status}}" stt-drill` and `docker --context desktop-linux logs --tail 40 stt-drill`. Expected: a growing restart count and `LocalEntryNotFoundError` in the log.
2. Remove it: `docker --context desktop-linux rm -f stt-drill`.
3. Filled volume, no network: repeat with the volume `oblivion-stt-models` mounted (not read-only: the Hugging Face client may write lock files) and the same variables. Expected: the container stays up and `/available` is true (`docker exec` a request to `127.0.0.1` inside the container, since `--network none` publishes nothing). Remove the container.
4. Remove the throw-away volume: `docker --context desktop-linux volume rm stt-drill-empty`.

## Acceptance criteria

- Step 1 shows the failure and the restart loop (or, if the engine is different, exactly what happens, in *Notes*).
- Step 3 starts offline from the volume.
- Only the throw-away container and volume were removed.

## Verification

The `ps`, `inspect` and `logs` outputs, in *Notes*.

## Notes

This is the evidence for the Known limitation about a crash loop and for the advice to fill the volume before the first start (T-02.3). If the maintainer decides later that the service should fall back or start without a model, that is a new decision task, not part of this plan.

## Result (2026-11-09)

Throw-away names only (`stt-drill`, `stt-drill-empty`); both were removed, and the real container, volume and the unrelated compose volume were not touched. **Step 1, empty volume, no network, `--restart unless-stopped`:** after 45 s the container was `Restarting (1)`, **restart count 9**, exit code 1, and the log ends in `LocalEntryNotFoundError: Got: ConnectError: [Errno -3] Temporary failure in name resolution`. This is the crash loop F11 predicted. **Step 3, the filled volume `oblivion-stt-models` mounted, no network:** the container was `Up`, restart count 0, and a request to `127.0.0.1:8001/available` from inside returned `is_available: true`. Afterwards `oblivion-stt-models` is still 551,212 KiB. The advice "fill the volume before the first start" (the run-time `prepare`, T-02.3) is what protects a normal deploy.
