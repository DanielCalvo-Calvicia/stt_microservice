## Goal

Install and run stt natively on the robot's Raspberry Pi (a Pi 4 or newer, 64-bit Raspberry Pi OS), with the deployment tool and the local engine, and measure whether `small.en` and the gate's `tiny.en` are fast enough, tuning `STT_THREADS`. The audit could only resolve the wheels (F16); the Pi was never used for stt, and "local model speed on a Pi is unknown".

## Read first

[../../deployment/deployment.md](../../deployment/deployment.md) (Portability), `deployment/docs/USER_GUIDE.md` (the Pi commands, `--system-deps`, `--remote`), the Notes of [T-01.1.3](../T-01_deployment-readiness/T-01.1_baseline-checks/T-01.1.3_real-transcription.md) (the PC's real-time factor).

## Files

None changed. Settings go in the maintainer's `deployment/config/local/` for the Pi's layout.

## Steps

This needs the **Raspberry Pi** reachable; the assistant prepares the commands and the maintainer runs them (or says go). The Pi's SSH address is the maintainer's (the Docker context `raspberry` uses one); do not assume it.

1. On the Pi: `python3 oblivion.py doctor --host <pi-machine>` and `validate`; record the Python version and the free RAM (`free -m`) and CPU model.
2. `python3 oblivion.py deploy --host <pi-machine> -s stt --system-deps --health-timeout 900` with `STT_ENGINE = "local"` and the gate on. Read: the install compiles nothing (wheels for aarch64), the `prepare` step downloads **both** models, the time to `healthy and available`.
3. Copy the WAV of T-01.1.3 to the Pi and repeat its calls (probes, batch, gate). Record, for `small.en` (main) and `tiny.en` (gate), the elapsed time and the real-time factor.
4. Tune: with the maintainer's settings file, try `STT_THREADS` 2 and 4 (and, if the maintainer wants, `STT_MODEL = "base.en"` or `tiny.en` for the main model), redeploy or restart, repeat step 3. Record the best values and the memory use during a call (`free -m` or `ps`).
5. With Brain's 60 s preflight in mind, `stop` and `start` stt and record the restart time with warm caches.

## Acceptance criteria

- stt installs from wheels and runs natively on the Pi; the models were downloaded by the `prepare` step, not at first start.
- *Notes* hold the real-time factors and the memory use for each model and thread count, and a recommendation (keep the defaults, or change `STT_THREADS` / the model for the Pi) for the maintainer.
- The speed numbers answer "is local STT usable on the Pi, and is the gate's delay acceptable" with a yes or a no and the numbers.

## Verification

The install lines, the timings and the memory readings, in *Notes*.

## Notes

If the Pi cannot run `small.en` at a usable speed, the findings go to the maintainer as a decision (use `STT_ENGINE=openai` on the Pi, a smaller model, or run stt on the server of the `pc-server-pi` layout); this task does not choose.

**The Pi, from the maintainer (2026-11-06, [Q01](../../questionnaires/Q01_before-the-deployment-tasks.md) question 14):** a Raspberry Pi **4B with 4 GB** of RAM, 64-bit Raspberry Pi OS **without a desktop** (Lite). The Debian release (bookworm or the newer one) is **not known**: step 1 reads `/etc/os-release` and records it, and the aarch64 wheels for that release's Python are checked before the install. Whether Docker is installed on it and whether the `raspberry` Docker context answers are **not known** yet (T-03.7 checks them). With 4 GB, watch the memory of `small.en` plus the gate's `tiny.en` together.

**Language and the time limit:** Spanish is planned for the future (question 6), so step 4 also measures a multilingual model (`STT_MODEL = "small"` with `STT_LANGUAGE = "es"` and a short Spanish sample), and reports the numbers beside the English ones. The maintainer gave no time limit (question 7: `UNKNOWN`), so this task only **reports** the times and the real-time factors; it cannot say pass or fail on delay.
