## Goal

Decide how a stt container gets its local models (the main model when `STT_ENGINE` is not `openai`, and the gate's), given that the model cache does not survive a recreated container and the `prepare` step has no settings at build time. It changes the deployment tool for every Docker user, so it is the maintainer's choice.

## Facts

- The Docker runtime recreates the container on every start (`docker rm -f` then `docker run`) and mounts only the generated `.env` read-only; it has no volume support (F8).
- `prepare` runs in the Dockerfile at **build** time with no `.env`, so for stt it sees engine `openai` and the gate off and returns at once (F7). The same line serves every service that declares a `prepare` in the catalogue (other services have one, and their downloaded files are baked into their images that way), so it cannot simply be removed.
- `HF_HOME` written in the generated `.env` is honoured by the service and by the fetch script, which load that file before importing the model libraries (F10).
- A first start with an empty cache downloads the model before the server listens (F11, F12); the deploy waits 60 s by default, Brain's preflight 60 s, and the user guide already says to add `--health-timeout 600` (F13). The time it really takes is measured in T-01.1.2.
- A runtime-specific setting has one hook, the computed layer of `resolve_env` (`SERVICE_HOST` becomes `0.0.0.0` for Docker); `HF_HOME` is in no `.env.example` and draws a "typo?" warning unless the catalogue lists it in `extra_env` (F9).
- The default engine is `openai`, which needs no model at all. The decision matters only for `STT_ENGINE=local` and for the gate.

## Options

| | Option | Cost | What a restart does |
|---|---|---|---|
| A | A named volume holds the cache (`HF_HOME` in it); the models download at the service's **first start** | the volume (T-02.2, T-02.4) | nothing to download after the first start; the first start is slow (needs `--health-timeout` and Brain's preflight to wait) |
| B | A, plus the tool runs the service's `prepare` script once in a throw-away container with the volume and the real `.env`, after the build and before the service starts (deploy, update, rollback), the place where the native path runs it | A, plus T-02.3 | the service never starts with an empty cache while the network is up; a download failure is a warning, as natively |
| C | Bake the models into the image at build time: the tool passes the model names as build arguments | settings must reach the build (today none do), +hundreds of MB per image, a rebuild to change a model | nothing to download, no volume; a model change needs a rebuild |
| D | Change nothing in the tool; document that Docker supports `STT_ENGINE=openai` and that a local engine runs natively, or re-downloads in every new container | none | every recreated container downloads again |

**Recommendation: B.** It is the Docker equivalent of the native `prepare` step, so the 60 s waits are not at risk on a normal deploy; it keeps the image free of models and secrets; it leaves other services' build-time `prepare` alone (a catalogue key chooses per service, question 3). Choose A if you accept a slow first start and want the smaller change; D if Docker for a local engine is not wanted.

## Questions for the maintainer

1. A, B, C or D?
2. If A or B: is a volume per service, named `oblivion-<service>-<name>` (here `oblivion-stt-models`) mounted at `/models`, with `HF_HOME=/models/huggingface` set by the tool **only for Docker** (the computed layer) acceptable? Native installs keep the default cache.
3. If B: should run-time `prepare` replace the build-time one only for services that say so in the catalogue (recommended: stt asks for it, the other services keep building theirs), or for all?
4. A failed download at deploy: a warning and the deploy continues (recommended, as natively), or the deploy fails for a service that needs the model?
5. Should `stop` or `rm` ever delete the volume? (Recommended: never automatically; the manual names `docker volume rm oblivion-stt-models` for the operator.)

## Resolution

**Decided by the maintainer on 2026-11-06** (answers of [Q01](../../questionnaires/Q01_before-the-deployment-tasks.md), questions 1 to 4):

1. **Option B.** A named volume holds the cache, and the tool runs stt's `prepare` script once in a throw-away container with the volume and the real `.env`, after the build and before the service starts (deploy, update, rollback).
2. **The volume:** `oblivion-stt-models`, mounted at `/models`, with `HF_HOME=/models/huggingface` set by the tool only for Docker. A native install keeps the default cache. Accepted.
3. **Which services get the run-time `prepare`:** not asked in Q01 (it concerns the other services' catalogue entries). The assumption of T-02.3 stands: a per-service catalogue key chooses it, stt asks for it, and no other entry changes.
4. **A download that fails during `deploy`:** a warning and the deploy continues, as it does natively; the service then fails its own start with a clear error. Accepted (recommended answer).
5. **Deleting the volume:** `stop` and `rm` never delete it automatically; the manual names `docker volume rm oblivion-stt-models` for the operator. Accepted (recommended answer).
