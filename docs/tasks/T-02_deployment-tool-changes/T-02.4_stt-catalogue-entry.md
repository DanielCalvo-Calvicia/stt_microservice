Declare the volume and the run-time `prepare` in the stt entry, and make the generated `.env` of a **Docker** stt set `HF_HOME` inside the volume, without changing a native install (F9, F10). **Written for option B of T-02.1.**

## Specification

- The generated `.env` of stt contains `HF_HOME=/models/huggingface` for `runtime = "docker"` and no `HF_HOME` for `native` (a test for each). A value the operator sets for `HF_HOME` in a local file still wins, with the existing warning about computed variables if it applies.
- `HF_HOME` is not added to stt's `.env.example`: a blank value in the `.env` would override the library's default (python-dotenv sets what the file says), and the service does not read the variable itself.
- The `prepare` line keeps pointing at `scripts/fetch_gate_model.py` (the file name stays, T-01.3.2).
- `internal` (not `extra_env`) is the catalogue key for a variable that is accepted and never advertised (`env_names.known_variables`, the header of the catalogue). Do not add `HF_HOME` to `EXTRA` in `scripts/env_inventory.py`.
- Do not change another service's entry. Run `..\brain_microservice\windows\Scripts\python.exe scripts\env_inventory.py --check` from `deployment/`: the generated `config/services/stt.toml` must not need a rewrite from this task (if it does, say why in *Notes* and ask).

## Acceptance criteria

- `catalogue` test: stt has `volumes`, `prepare_at_run`, `docker_env` and `extra_env` as declared; another service has the defaults.
- `resolve_env` tests: Docker adds `HF_HOME`, native does not, a local override wins.
- `oblivion.py validate --host <machine> --config <throw-away folder>` with stt set to `runtime = "docker"` does not warn about `HF_HOME`, and `env_inventory.py --check` passes.
- The deployment suite passes.

## Verification

Run the deployment tests in the background; use `--config <a throw-away config folder>` for `validate` and `env` so the maintainer's `config/local/` is not touched.
