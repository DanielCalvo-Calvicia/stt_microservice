## Goal

For a Docker service that asks for it, run its `prepare` script once, inside a throw-away container made from the built image, with the generated `.env` and the service's volumes, before the service container starts. This gives the container the same step the native path has (F7), now that the script fetches the main model too (T-01.3.2). **Written for option B of T-02.1.**

## Specification

- A service that does **not** set the flag behaves exactly as today in Docker: the Dockerfile runs `prepare` at build time with `|| echo "warning: prepare step failed"`. Do not edit the `RUN` line of the Dockerfile unless the neighbouring plan has not already changed it; if it has, keep its change.
- The throw-away container uses the same image, `--mount` of the `.env` (read-only, at `/app/.env`) and of the volumes, and runs `python <prepare ...>` from `/app`. It sees the same settings as the service, including `HF_HOME` (T-02.4).
- A non-zero exit prints the warning and the deploy goes on, as natively (decided in T-02.1, 2026-11-06: a warning and continue).
- `--dry-run` shows the `docker run --rm ...` line and runs nothing; the line goes through `Shell`.
- Do not run it in `start` (only deploy, update and rollback call `prepare` natively, F7); the models are in the volume afterwards.

## Acceptance criteria

- A test with the fake `Shell`: for a service with the flag, `deploy` runs `docker build` (without the `PREPARE` build argument), then the `docker run --rm` of the prepare command with the `.env` and the volume mounts, then the service `docker run`, in that order; for one without the flag the order and the arguments are those of today.
- A test that a failing prepare prints the warning and does not stop the deploy.
- The deployment suite passes.

## Verification

Run the deployment tests in the background. The real run is in [T-03.2](../T-03_docker-and-arm64-acceptance/T-03.2_run-and-call.md).

## Notes

If another service's plan makes the build fail when its `prepare` fails (a `prepare_required` key), the two keys must not conflict: `prepare_at_run` services are not built with the `PREPARE` argument at all.
