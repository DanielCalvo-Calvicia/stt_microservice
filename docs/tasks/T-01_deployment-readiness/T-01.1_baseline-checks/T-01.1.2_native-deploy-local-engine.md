## Goal

Deploy stt with the deployment tool the way the robot will really be deployed, with `STT_ENGINE=local` and the gate on, and record **what the `prepare` step fetched, what the first start downloaded, and how long the service took to answer `/available`** (F5, F7, F12, F13). That time is attached to ADR-009 (the decision T-02.1 was taken on 2026-11-06 before it was measured) and decides whether `--health-timeout` advice is still needed.

## Read first

`deployment/CLAUDE.md`, [../../../deployment/deployment.md](../../../deployment/deployment.md), `deployment/docs/USER_GUIDE.md` (the commands), the `[services.stt]` entry of `deployment/config/catalogue.toml` (F6).

## Files

None changed in this repository. The tool writes in its own work directory (the clone of stt, its `.env`, its logs). Do **not** edit `deployment/config/` for this check. The settings for the run go in the maintainer's own `deployment/config/local/stt.toml` (git-ignored): ask the maintainer to add, and to remove afterwards, only

```toml
[env]
STT_ENGINE = "local"
STT_GATE_ENABLED = 1
```

Never open `config/local/*.toml` to read a key; `oblivion.py env` prints the settings with secrets masked.

## Steps

Run from `deployment/`, with a machine of the layout in `config/robot.toml` (`<machine>`; `oblivion.py layouts` lists them):

```powershell
$py = "..\brain_microservice\windows\Scripts\python.exe"
& $py oblivion.py doctor   --host <machine>
& $py oblivion.py validate --host <machine>
& $py oblivion.py env      --host <machine> stt        # secrets are masked; shows the file each value came from
& $py oblivion.py plan     --host <machine> -s stt     # read-only
```

Then, **after the maintainer says yes** (it clones, installs, may download models, starts a process):

```powershell
Measure-Command { & $py oblivion.py deploy --host <machine> -s stt --health-timeout 600 }
& $py oblivion.py status --host <machine>
& $py oblivion.py logs   --host <machine> -s stt --lines 60
```

Read in the `deploy` output: the `prepare` step of stt (it should load only the **gate** model, F5, and print `Gate model tiny.en is ready`), the time until `healthy and available`, and whether a model was downloaded **after** the `prepare` step (the `Loading local Whisper model on CPU` log line for the main model, then `Local Whisper model loaded`). Run `stop` and then `start` (`& $py oblivion.py stop --host <machine> -s stt`, then `start`, timed the same way) and record the time again: the models are now cached.

To see the 60 s problem (F13) the first start must happen with the default `--health-timeout` on a **cold** cache. Do that only if the maintainer wants it and gives you an empty Hugging Face cache folder to use through `HF_HOME` in a throw-away `config/local/stt.toml` (`HF_HOME` is not documented by the service, so `validate` will warn; that is expected). Never delete the maintainer's own cache.

## Acceptance criteria

- `doctor` and `validate` have no error (warnings are listed in *Notes*).
- `deploy` finishes and `status` shows stt healthy on port 8001 with the engine `local` and the gate on.
- *Notes* say which models the `prepare` step fetched (expected: the gate's only), which model the first start fetched, the elapsed time of the first and the second start, and the Hugging Face cache folder used.

## Verification

The relevant lines of `env`, `deploy` (the prepare step and the health line), `status` and the stt log, with the two timings, pasted in *Notes* (no key).

## Notes

Record which Python version the tool picked, whether it used the shared-logging wheel from `libs/`, and the sizes of the downloaded models (`small.en` and `tiny.en` folders in the cache). If `status` is healthy but the first start took longer than 60 s, say so: attach it to ADR-009 as a dated note; it also decides the `--health-timeout 600` advice already in the user guide.

### Findings

1. **The 60 s problem (F13) did not show up on this machine and connection:** the cold wait for the main model was about 28 s, under the default 60 s of both the deploy wait and Brain's preflight. This is **one data point on a PC with a fast connection**, not the Pi: the Pi's download and especially its load time are unmeasured (T-03.6). The default-timeout cold run was not repeated separately because the measured wait is already below 60 s.
2. The first start did download the main model **after** `prepare`, as F5 and F11 predicted; `prepare` does not cover it (T-01.3.2).
3. `huggingface_hub` warned that this Windows machine does not support symlinks in the cache (no Developer Mode): files are copied instead, still working, "degraded" disk use. It also warned that requests to the hub are unauthenticated. Both are harmless here and appear in the deploy output and the service log.
4. At INFO level the service log is dominated by `httpx2` request lines from the hub downloads (first start only).
5. **The `deployment` repository's uncommitted work grew while this plan was written:** besides the files noted in F14, it now also has changes in `docker/service.Dockerfile`, `infrastructure/outbound/runtime/docker_runtime.py` (a `PREPARE_REQUIRED` build argument from a new `prepare_required` catalogue key), `domain/entities/service_spec.py`, `infrastructure/config/catalogue_loader.py`, `infrastructure/outbound/health/http_health.py` and two new test files (`tests/test_health_wait.py`, `tests/test_prepare.py`). They are not part of this run and not mine. T-02.2 to T-02.4 touch the same files and must read `git diff` first (they already say so) and check whether `prepare_required` changes the shape of the run-time `prepare` of ADR-009.
