## Goal

Show, on a real deploy, how the service fails when it cannot start, so the plan fixes the right things: an OpenAI engine without a key, a local model that is not in the cache and cannot be downloaded, and a mistyped gate model. These are the claims of the audit and of F11.

## Read first

[../../../operations/monitoring.md](../../../operations/monitoring.md) ("Start-up"), [../../../configuration/environment-variables.md](../../../configuration/environment-variables.md) (no validation of the values), facts F6, F11, F12 and F13.

## Files

None changed in the repositories. The drills use the maintainer's git-ignored `deployment/config/local/stt.toml` (restored at the end) and a **throw-away Hugging Face cache folder** given through `HF_HOME`. The maintainer's real cache is never touched.

## Steps

Ask before each deploy.

1. **No key.** Engine `openai`, no key anywhere. `oblivion.py validate --host <machine>` should report the missing `OPENAI_API_KEY` as an error (the catalogue `require` rule). Record what `validate` and then `deploy -s stt` say. If the deploy still starts the service, record the service's own message (`EngineNotConfigured`) and its exit; if the tool refuses first, say so and run `python main.py` by hand from the stt folder with the engine `openai` and no key to see the service's message.
2. **Cold cache, no network.** Engine `local`, `HF_HOME` pointing at an empty folder in the scratchpad, `HF_HUB_OFFLINE=1` in the same local settings file. `deploy -s stt`: expected, the `prepare` step (gate off) does nothing, the service exits at start with `LocalEntryNotFoundError` (F11), the deploy reports it unhealthy. Record how the deploy tool words it and what `logs` shows.
3. **Mistyped gate model.** Gate on, `STT_GATE_MODEL = "tiny.en-typo"`, network on. Expected: the `prepare` step warns (`Could not load the gate model ...`, exit 1) and the deploy continues; the service then fails at start when it builds the gate. Record both messages.
4. **Slow first start.** Engine `local`, the same empty throw-away cache, network on, default `--health-timeout`. Record whether the deploy times out at 60 s while the service is still downloading (F13), and what `status` shows afterwards.
5. Restore the settings file and the environment; stop stt.

## Acceptance criteria

Steps 1 to 4 behave as read in the code (or the differences are written down), with the exact messages and exit behaviour in *Notes*; the settings file and the throw-away cache are removed.

## Verification

The pasted messages, with no key.

## Notes

These results feed T-01.3.2 (what `prepare` must do when a model cannot be fetched), ADR-009 (a slow or failing first start) and T-03.5 (the same drill in a container). `restart: unless-stopped` of the Docker runtime is not in play natively: do not claim a crash loop from this task.

## Result (run on 2026-11-06)

Run by the assistant after the maintainer said "go", on the scratch deployment of T-01.1.2 (`C:\stt_t0112`, Windows 11). For each drill the scratch `config/local/stt.toml` was rewritten and the service was deployed with `oblivion.py --config C:/stt_t0112/config ... deploy -s stt`; the maintainer's own `config/local/` files and Hugging Face cache were not used. No real key was involved (drill 5 used an obviously fake one). Every message below is pasted without a key.

### Drill 1: the OpenAI engine without a key (no key anywhere)

- `validate`: `error: stt: OPENAI_API_KEY is required when STT_ENGINE=openai; set OPENAI_API_KEY = "..." in config/local/stt.toml (or in config/local/all.toml for every service that uses it)`, `1 error(s)`, exit code 1.
- `deploy -s stt`: the tool **refuses before starting anything**: after fetching the code, `FAILED: - stt: OPENAI_API_KEY is required when STT_ENGINE=openai; set ...`, exit 1, 1 s. `status`: stt `stopped`.
- `main.py` started by hand (engine `openai`, no key): exits with code 1 and a **full Python traceback** ending in `application.errors.EngineNotConfigured: OPENAI_API_KEY is required for OpenAI STT engine`. The service itself gives no clean one-line message; the clear message comes from the deploy tool.

### Drill 2: the local engine, an empty cache, no network (`HF_HOME` on an empty folder, `HF_HUB_OFFLINE=1`, gate off)

- `validate`: OK, with two warnings that `HF_HOME` and `HF_HUB_OFFLINE` are "not documented by the service (typo?)", as expected.
- `deploy -s stt`: `prepare` printed `STT_GATE_ENABLED is off: no gate model needed` (it does nothing, F5), the service started in its window, and the tool waited and ended with `FAILED: stt: health: no answer (<urlopen error [WinError 10061] ...connection refused>)`. Exit 1 after **62 s**: it waited the whole default health timeout although the service had died within seconds. `status`: `UNHEALTHY` with the same text. The Windows error text arrives garbled (a Spanish message read with the wrong code page).
- `logs`: a traceback ending in `huggingface_hub.errors.LocalEntryNotFoundError: Cannot find an appropriate cached snapshot folder for the specified revision on the local disk and outgoing traffic has been disabled. To enable repo look-ups and downloads online, set 'HF_HUB_OFFLINE=0' ...`, then `=== stt exited with code 1`. F11 confirmed. The reason is only in the log, not in the deploy output.

### Drill 3: a mistyped gate model (`STT_GATE_ENABLED=1`, `STT_GATE_MODEL=tiny.en-typo`, network on, main model cached)

- `validate`: OK (no check of the value).
- `deploy -s stt`: the `prepare` step printed `Could not load the gate model tiny.en-typo: Invalid model size 'tiny.en-typo', expected one of: tiny.en, tiny, base.en, base, small.en, small, medium.en, medium, large-v1, large-v2, large-v3, large, distil-large-v2, ...` and `warning: stt: scripts/fetch_gate_model.py failed (1); see above`. The deploy **continued**, started the service, waited **63 s** and ended `FAILED: ... health: no answer`.
- `logs`: the service died building the gate: `ValueError: Invalid model size 'tiny.en-typo', expected one of: ...`, then `stt exited with code 1`. As read in the code.

### Drill 4: a slow first start (local engine, an empty cache, network on)

- With the **default** health timeout the deploy did **not** time out on this machine: `healthy and available` after **42 s** in total. The service log shows the main model downloaded and loaded between 20:20:17 and 20:20:55 UTC, **38 s** (28 s on the first run of T-01.1.2: the download time varies), under the 60 s of the tool and of Brain.
- A simulation of a slow link, clearly **not** a real slow download: the same cold start with `--health-timeout 10`. The deploy ended `FAILED: ... health: no answer` after 14 s and `status` showed `UNHEALTHY` while the service was in fact still downloading. **45 s later `status` showed `running  healthy and available`** and `/available` was true. So when the first start outlives the wait, `deploy` exits 1 and says unhealthy although the service becomes healthy by itself (the F13 mechanism is confirmed). What Brain's own preflight does in the same case was not tested.

### Drill 5 (extra, not in the task): a wrong OpenAI key, tested with an obviously fake one

- The service starts and `/available` answers `is_available: true` (it never calls the API, as documented).
- `POST /process/batch` answers **500** with `message` and `data` = `Error code: 401 - Incorrect API key provided: sk-fake-*********************0000. You can find your API key at https://platform.openai.com/account/api-keys.`, and the log has `Operation failed action="process_batch" error="AuthenticationError: Error code: 401 - Incorrect API key provided: sk-fake-*********************0000. ..."`.
- **The OpenAI library masks only the middle: the first 8 and last 4 characters of the key reach the caller and the log.** This closes the "not verified" point of the security document: it is a leak. Not fixed here (see findings).

### Findings

1. The tool and the service together fail **clearly** only for a missing key (drill 1). A cold cache offline or a mistyped model are visible only in the log; the deploy output says "health: no answer" (drills 2 and 3).
2. **The deploy waits the whole health timeout even when the service has already exited.** The log line `stt exited with code 1` exists; the tool could stop waiting. A point for the `deployment` repository, not fixed here.
3. `prepare` (`fetch_gate_model.py`) already behaves as the plan assumes: with the gate off it does nothing; a bad name is a warning and exit 1, and the deploy goes on. T-01.3.2 keeps that rule for the main model: a failed download is a warning, never a failed deploy (also the maintainer's answer on the Docker download, ADR-009).
4. A first start with an empty cache downloads before the server listens (38 s here); if it takes longer than the wait, `deploy` reports failure for a service that is about to be healthy.
5. **New debt (security):** the wrong-key message echoes part of the key (drill 5). It is now written in `security.md`, `monitoring.md`, the architecture debt list (item 10), the README limitations and NFR-4. A fix (a fixed message for the OpenAI engine, and only the exception type in the log) is a small code change; the maintainer said yes and it is now task [T-01.7](../T-01.7_hide-openai-error-text.md).
6. `restart: unless-stopped` is not in play natively; no crash loop was claimed.

### Left behind

Settings restored to the local-engine file of T-01.1.2; the generated `.env` (fake key) and the throw-away cache `hf_empty` deleted; the service stopped; port 8001 free. The scratch folder `C:\stt_t0112` (about 1 GB with the first cache) is kept only until the end of T-01.1; T-01.1.6 and T-01.1.7 do not need it.
