## Goal

Prove the **default** engine on a deploy: `STT_ENGINE=openai` with a real key calls the Whisper API and returns text, and `/available` is true without calling the API. The real API has not been called in the last documentation pass (README, *Status*).

## Read first

[../../../security/security.md](../../../security/security.md) (what leaves the machine), [../../../operations/monitoring.md](../../../operations/monitoring.md) (`/available` does not call the API), `deployment/config/local/README.md` (where a key goes), `deployment/docs/DEPLOYMENT.md` section 5.2.

## Files

None changed in the repositories. The maintainer's own `deployment/config/local/all.toml` (or `stt.toml`) must hold `OPENAI_API_KEY`: **the assistant never reads, prints or copies it**. Use `oblivion.py env --host <machine> stt`, which masks it, to confirm it is set.

## Steps

1. Ask the maintainer: this sends a few seconds of synthetic speech to OpenAI and costs a few tokens. Wait for the yes.
2. Settings for the run: `STT_ENGINE = "openai"` (the catalogue default; remove the override of T-01.1.2) and the gate off. `oblivion.py validate --host <machine>` must show no error: the catalogue requires the key when the engine is `openai` (F6).
3. `oblivion.py deploy --host <machine> -s stt` (ask first), then `status`.
4. `GET <stt-base-url>/available`: `true`, immediately, with no network call.
5. `POST <stt-base-url>/process/batch?sample_rate=<rate>` with the PCM of T-01.1.3. Record the text.
6. Optional: set `STT_PROMPT` to the wake phrase in the local settings, redeploy, and send a silent buffer (a few seconds of zero samples): record whether the model returns the prompt words for silence (the `.env.example` warns about it).
7. Restore the maintainer's local settings file.

## Acceptance criteria

- `deploy` finishes and `/available` is true; the batch route returns the phrase.
- The stt log shows `Calling OpenAI transcription API` and `OpenAI batch transcription completed` with lengths and the model name, never the text or the key.
- No key appears in any output pasted into *Notes*.

## Verification

The call result and the log lines, in *Notes*.

## Notes

If the key is missing, `validate` should say so before the deploy and the service must not start with `EngineNotConfigured` unexplained; the drill for that is in [T-01.1.5](T-01.1.5_failure-drills.md).

## Result (run on 2026-11-06)

Run by the assistant after the maintainer said "go", on the scratch deployment of T-01.1.2 (`C:\stt_t0112`, Windows 11, the same machine as T-01.1.3).

**How the key reached the run (the maintainer chose this out of four options):** the deploy tool reads secrets only from `<config>/local/`, so a short script, run with its output hidden, took **only** `OPENAI_API_KEY` from the maintainer's `deployment/config/local/all.toml` and wrote it, with `STT_ENGINE = "openai"`, into the scratch `C:\stt_t0112\config\local\stt.toml`. The key was never printed or put in a document. After the test the script and that file were deleted, the earlier local-engine settings were restored, the generated `.env` was removed, and a search of the scratch config, logs, state, clone, deploy log, audio and scripts found no key-like string. **One exposure to know about:** the assistant's tooling showed the contents of the scratch settings file once (an automatic notice that a file had changed), so the key value appears in this session's transcript. If that matters, rotate the key.

**Settings and deploy:** `validate` OK; `env` showed `STT_ENGINE=openai` and `OPENAI_API_KEY` (masked) from `config/local/stt.toml`, the gate off (default). `deploy -s stt` (no `--health-timeout`): **4 s**, `dependencies unchanged, skipping install`, the `prepare` step printed `STT_GATE_ENABLED is off: no gate model needed`, then `healthy and available`.

**Probes** (the probe script of T-01.1.3 with `--no-gate`): `/health` 200 (15 ms); `/available` 200 `is_available: true` in **2 ms**, with no network call; `/gate/available` **404** (the gate is off, as documented).

**Batch route, `whisper-1`:**

| Audio | Text returned | Elapsed (two calls) |
|---|---|---|
| `phrase.wav`, 3.78 s | `Oblivion 306, what time is it?` | 2.69 s, 0.74 s |
| `other.wav`, 2.11 s | `The weather is nice today.` | 1.51 s, 1.10 s |

Exact text. The main shared stream gave the same text (round trip 1.16 s and 0.95 s). An empty body gave `400`. Compared with the local engine on the same machine (4.5 to 5 s), the API was 3 to 6 times faster per utterance, and its time does not depend on the CPU of the robot, only on the network.

**Logs:** per call `Calling OpenAI transcription API` with `model="whisper-1"`, `language="en"`, `prompted=false` or `true`, and `OpenAI batch transcription completed` with `text_length`; no key-like string (0 hits for `sk-`) and none of the spoken text (0 hits) in `stt.log`.

**Optional step 6 (silence and `STT_PROMPT`):** a 3 s buffer of zero samples gave the text **`you`** without a prompt, and an **empty** text with `STT_PROMPT` set to the wake phrase (one sample each; the phrase itself came back unchanged with the prompt). The prompt change was appended to the scratch settings and redeployed (4 s). Not a conclusion: more samples would be needed.

**Cost:** 11 API calls, about 35 s of audio in total (under one cent at the published `whisper-1` price per minute).

### Findings

1. The default engine works end to end on a deploy: `/available` is true without an API call, the text is exact, the logs are clean (NFR-4 on the OpenAI path).
2. **The two engines differ in the batch text:** the OpenAI engine strips it, the local engine keeps Whisper's leading space (the stream routes strip both). Documented in `api.md` now.
3. **A silent utterance can produce the text `you`** with the OpenAI engine and no prompt; `SttService` only drops an empty text (FR-2), so Brain would receive it as speech. This is a Brain/microphone-side concern (the microphone cuts utterances) and a reason to keep `STT_PROMPT` set; not changed here.
4. `oblivion.py env --host pc stt` (a host that does not run stt in the maintainer's layout) ends in a Python traceback (`KeyError: 'stt'`) instead of a message; a tool robustness point for the `deployment` repository, not part of this plan.
5. The maintainer's real `~/oblivion` work directory already has an stt install; it was not touched.
